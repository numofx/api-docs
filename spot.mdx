The cNGN-USDC spot market quotes cNGN in USDC. Every price the Numo API reports for it — on the
book, in trades, in candles, and in the `ui_intent` you submit — is **USDC per cNGN**, about
`0.00073`, and every size is a quantity of **cNGN**. Read this before integrating against spot.

<Note>
  **What changed.** Since 2026-10-07 the pair is quoted as
  cNGN-USDC: base cNGN, quote USDC. Before that it was quoted the other way, as USDC priced in cNGN
  with sizes in USDC, and the API translated between the two.

  - The identifiers changed on 2026-10-08, after the orientation did: `cNGN-USDC` and `cNGN-PERP`
    are now what you pass as `symbol`, `market` and `ticker_id`, matching `display_name`. The old
    `USDCcNGN-SPOT` and `USDCcNGN-PERP` remain deprecated aliases until 2027-01-06 (see the note
    under [Discover the market](#discover-the-market)).
  - If you read `/v1/integrations/tickers`, `/orderbook` or `/trades`: `base_currency` is now `cNGN`
    and `target_currency` `USDC`. Prices are USDC per cNGN, `base_volume` and book quantities are
    cNGN, `target_volume` is USDC. A `buy` is a buy of cNGN.
  - If you submit `ui_intent`: send `order_entry_spec: "cngn_usdc_spot_v1"` (or
    `cngn_usdc_perp_v1` on the perp), a price in USDC per cNGN, a size in cNGN, and the side you mean
    in cNGN. The engine order is now identical to the intent — nothing is inverted, and no formula
    stands between them. The old `usdc_cngn_*_v1` specs are refused.
  - If you read `ui_intent` on orders, trades or fills: `price` is USDC per cNGN, `size` is cNGN, and
    `side` equals the engine side.
  - `stats_24h` and candles were already in this orientation and did not change. The remarks about
    reading `1/high` as a low no longer apply: `high` is the high.

  To show a naira rate, compute `1 / price` yourself. The Numo app shows it as a secondary line only.
</Note>

## Discover the market

```bash
curl "https://api.numofx.com/v1/markets"
```

Look for:

- `market = "cNGN-USDC"`
- `display_name = "cNGN-USDC"`
- `contract_type = "spot"`
- `base_asset_symbol = "cNGN"` and `quote_asset_symbol = "USDC"`
- `order_entry_spec = "cngn_usdc_spot_v1"`

Prefer the `market` symbol over `asset_address` and `sub_id` when you call the read endpoints. The
symbol is stable; the address pair can change between deployments.

<Note>
  **Deprecated identifier.** Until 2027-01-06 the old identifier `USDCcNGN-SPOT` is accepted as an
  exact-match alias for `cNGN-USDC` everywhere an identifier is read: `symbol`, `market` and
  `ticker_id`. A request that uses it returns the same data as one that uses `cNGN-USDC`, names the
  market `cNGN-USDC` in the body, and carries two response headers: `Deprecation: true` and
  `X-Canonical-Market: cNGN-USDC`. Switch to `cNGN-USDC` before the removal date.
</Note>

## Read the current price

```bash
curl "https://api.numofx.com/v1/book?symbol=cNGN-USDC"
```

Every order in the response carries a `spot_contract` object that restates it at the scales a
display uses. A bid to buy 137,400 cNGN at 0.0007278 USDC each looks like this:

```json
{
  "side": "buy",
  "limit_price": "0.0007278",
  "desired_amount": "137400",
  "spot_contract": {
    "spec": "cngn_usdc_spot_v1",
    "ui_intent": { "side": "buy", "price": "0.0007278", "size": "137400" },
    "engine_order": { "side": "buy", "price": "0.0007278", "amount": "137400" },
    "balance_delta": { "usdc": "-99.99972", "cngn": "+137400" }
  }
}
```

`ui_intent` and `engine_order` are the same order. The only difference is scale: `ui_intent` prints
the price to 10 decimal places and the size to 6, while `engine_order` and the top-level
`limit_price` and `desired_amount` carry the engine's full 18 places. Read whichever suits your
parser; they never disagree.

<Warning>
  A price near `0.0007` is correct, not a broken response. The quote currency is USDC, so one cNGN
  costs a fraction of a dollar.

  If your display wants naira per dollar, compute `1 / price` — `1 / 0.0007278 = 1373.99` — and
  label it as a derived figure. Do not feed the reciprocal back into an order: `ui_intent.price`
  is always USDC per cNGN.
</Warning>

`GET /v1/markets` publishes the contract inline on the spot entry, so you can assert it at runtime
rather than hardcoding it:

| Field | Value |
| --- | --- |
| `ui_price_unit` | `USDC per cNGN` |
| `ui_size_unit` | `cNGN amount` |
| `ui_side_meaning` | `BUY acquires cNGN and pays USDC; SELL delivers cNGN and receives USDC.` |
| `engine_price_unit` | `USDC per cNGN` |
| `engine_amount_unit` | `cNGN amount` |
| `engine_side_policy` | `same_as_ui` |
| `ui_price_to_engine` | `engine_price = ui_price` |
| `ui_size_to_engine` | `engine_amount = ui_size` |

## Book sides read the normal way

`bids` are orders buying cNGN and `asks` are orders selling it, and the trader's side is the engine's
side:

| Array | Side | What it means for you |
| --- | --- | --- |
| `bids` | buy cNGN | the price at which you can **sell** cNGN for USDC |
| `asks` | sell cNGN | the price at which you can **buy** cNGN with USDC |

Each order also carries `spot_contract.ui_intent.side`, which is the same value as its top-level
`side`.

A mid price:

```bash
curl -s "https://api.numofx.com/v1/book?symbol=cNGN-USDC" | python3 -c '
import json, sys
book = json.load(sys.stdin)
bid = float(book["bids"][0]["spot_contract"]["ui_intent"]["price"])
ask = float(book["asks"][0]["spot_contract"]["ui_intent"]["price"])
mid = (bid + ask) / 2
print(f"bid  {bid:.7f} USDC per cNGN")
print(f"ask  {ask:.7f} USDC per cNGN")
print(f"mid  {mid:.7f} USDC per cNGN  ({1 / mid:.2f} cNGN per USDC)")'
```

## Prefer the book over the last trade

`GET /v1/trades` returns the most recent fills, each with its own `spot_contract`. That is the right
source for a "last traded at" display, and every trade carries `created_at` so you can show its age.

It is the wrong source for a current rate. In a quiet period the last fill can be hours or days old,
and the endpoint returns it without any staleness signal — a stale price and a fresh one look
identical. The book quotes continuously, so a mid price stays current even when nothing is trading.

<Note>
  Check that `bids` and `asks` are both non-empty before computing a mid. If no maker is quoting,
  the arrays come back empty.
</Note>

## Candles and 24h stats

```bash
curl "https://api.numofx.com/v1/candles?symbol=cNGN-USDC&interval=1h&limit=200"
```

Candle prices and `stats_24h` are raw engine values with no `spot_contract` wrapper. They are in
the same unit as everything else — USDC per cNGN — so use them as they are: `high` is the highest
price paid for a cNGN in the bucket, `volume` is cNGN traded and `quote_volume` the USDC it traded
for. Buckets with no trades are absent rather than zero-filled.

## Polling and streaming

No rate limit is enforced. Polling every one to five seconds is ample for a displayed rate; be
considerate rather than aggressive.

For anything latency-sensitive, subscribe to the [websocket stream](/api-reference/websocket)
instead. Use the `book` and `trades` channels with `"market": "cNGN-USDC"`, seed from the
`snapshot` frame, and apply `update` deltas. Public channels need no authentication, and
server-side clients are unaffected by the browser origin allowlist.

## Submitting spot orders

Send the order you mean in `ui_intent`, with `order_entry_spec` set to the market's own spec. The
engine order is the identity of the intent:

```text
engine_side   = ui_side
engine_price  = ui_price      (USDC per cNGN)
engine_amount = ui_size       (cNGN)
```

So the values you sign into `action_json.data` are the same numbers as `ui_intent`, scaled to wei.
There is no inversion and no derived size any more. When you also send `side`, `limit_price` or
`desired_amount`, each must equal the corresponding `ui_intent` field or the order is rejected.

A fill of the whole order moves balances by `balance_delta`: a buy of size `S` at price `P` is cNGN
`+S` and USDC `-S x P`; a sell is cNGN `-S` and USDC `+S x P`.

`order_entry_spec` and `ui_intent` are accepted on the two markets that carry the contract —
`cNGN-USDC` with `cngn_usdc_spot_v1` and `cNGN-PERP` with `cngn_usdc_perp_v1` — and
refused everywhere else. The spec must be the market's own: an intent sent with the other market's
spec, or with a retired `usdc_cngn_*_v1` spec, is rejected with
`order_entry_spec must be "cngn_usdc_spot_v1" for this market's ui_intent`. Omit both fields to
submit raw engine values, which on these markets are the same values anyway.

See [Authentication and signing](/signing) for building the signed payload, and
[Create order](/api-reference/endpoint/create) for the full request body.

## Fees follow arrival order, not identity

`GET /v1/markets` reports the schedule for each market as `taker_fee_bps` and `maker_fee_bps`.
Read it from there — it is the only source, and the matcher charges exactly what it says.

The fee is paid by the **taker**, and taker is decided per fill by which of the two orders was
created **later**. It is not a property of an account, a strategy, or an order type.

<Warning>
  Resting a quote does not make you the maker. If your order arrives after the one it matches
  against, you are the taker on that fill and you pay the taker fee — even if you have been sitting
  on the book for hours, and even if you think of yourself as a market maker.

  A bot that requotes frequently is the later order most of the time, so it is usually the taker.
</Warning>

The practical consequence is the bound you sign. `worstFee` caps what a fill may charge you, and
the contract reverts `TM_FeeTooHigh` rather than filling when the charge exceeds it. Signing `0`
is safe only while a market charges nothing; on a market with a taker schedule it means every fill
where you arrive second reverts, silently and repeatedly, until the order expires.

Two details that decide the number:

- **`worstFee` is per unit filled, not a total.** The contract compares `fee / amountFilled`
  against it, so the correct bound is `feeRate x price`, and it changes with price. A single
  configured constant is right at exactly one price.
- **Leave headroom above the published schedule.** Orders already resting were signed under the
  old number, and they cannot be re-signed atomically with a fee change. Our own clients sign 30
  bps against a 25 bps schedule for this reason.

See [Authentication and signing](/signing) for how to compute and encode it.
